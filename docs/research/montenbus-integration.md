# Montenbus integration options

Checked **19 November 2026**. This builds on [the Montenbus section of the transport inventory](passy-transport-data.md#montenbus-stop-data-exists-booking-integration-remains-a-gap), [Montenbus membership prices](shuttles-lifts-fares.md#fares-for-a-journey-planner) and [the MOTIS contract](motis-api.md). It does not repeat their findings.

Today the app shows 392 points from the operator's Google My Maps export ([`scripts/prepare.py`](../../scripts/prepare.py)), each linking to the Via web app's home page with "Sur réservation. Adhésion nécessaire. Horaires non calculés." ([`src/PlaceCard.tsx`](../../src/PlaceCard.tsx)). MOTIS never sees Montenbus.

## Summary

- **No official Montenbus dataset exists** on transport.data.gouv.fr, data.gouv.fr or in the Oùra regional aggregate. The operator map is still the only machine-readable stop source, with no licence.
- **The holder can produce one.** Via's Service Design tool has an early-access **GTFS-Flex export**, aimed at "participating MaaS apps". On-demand static data falls under the EU MMTIS regulation, whose publication deadlines have passed.
- **MOTIS 2.11.4 already routes GTFS-Flex.** The `FLEX` mode is used for first/last-mile and direct legs, with no extra config key. Booking-rule output is on `master` only, not in a release.
- **Via publishes no public API, deep-link or quote documentation.** The public web bundle contains an undocumented `/proposal` deep-link handler that accepts origin, destination and time. Its behaviour on the web app was not verified, and it is not a supported contract.
- **Recommendation:** improve the card now. Then prototype Montenbus as a MOTIS `FLEX` service from a self-authored feed, labelled "à confirmer", and ask CCPMB for the official GTFS-Flex export, a licence and a supported deep link.

### Legal frame

- The EU MMTIS regulation, [Delegated Regulation 2017/1926](https://eur-lex.europa.eu/legal-content/FR/TXT/HTML/?uri=CELEX:32017R1926), defines on-demand transport as a service "qui se caractérise par la flexibilité des itinéraires" (art. 2(17)). Its [2024/490 amendment](https://eur-lex.europa.eu/legal-content/FR/TXT/HTML/?uri=CELEX:32024R0490) lists, for on-demand transport, location search, trip planning, auxiliary information and "modalités de réservation des services de transport à la demande" (annex 1.3 b). Static data for the whole EU network was due by **1 December 2023**, and on-demand fare items by **1 December 2024** (art. 4(3)(d)–(e)). The PAN's [deadline page](https://doc.transport.data.gouv.fr/le-point-d-acces-national/cadre-juridique/dates-limites-de-publication) gives the same dates.
- In French law, [Code des transports L1115-1](https://www.legifrance.gouv.fr/codes/section_lc/LEGITEXT000023086525/LEGISCTA000039670430/) (in force since 3 May 2025) implements 2017/1926. Under 3°, the authorities that organise services are responsible for supplying the data and may delegate this to operators. The PAN's [scope page](https://doc.transport.data.gouv.fr/le-point-d-acces-national/cadre-juridique/donnees-et-modes-de-transports-concernes) lists on-demand data items, including booking modalities, operating hours, access nodes and network topology. _Inference:_ CCPMB organises Montenbus ([regulation art. 1](https://www.montenbus.fr/reglement-montenbus/)), so these obligations plausibly apply to it. I have not verified CCPMB's formal status as a mobility authority (AOM).
- **Formats.** The regulation requires NeTEx/SIRI using the national profiles, or a format whose interoperability can be demonstrated ([formats page](https://doc.transport.data.gouv.fr/le-point-d-acces-national/cadre-juridique/formats-requis)). The French NeTEx profile [_Description des réseaux_ v2.4](https://normes.transport.data.gouv.fr/normes/netex/reseaux/) has a section "La flexibilité des lignes (TAD)", covering `FlexibleLine`, `FlexibleRoute` and `BookingArrangements`. The [_Horaires_ profile](https://normes.transport.data.gouv.fr/normes/netex/horaires/) covers `FlexibleServiceProperties`. The PAN's own ["TAD zonal" guidance page](https://doc.transport.data.gouv.fr/type-donnees/operateurs-de-transport-regulier-de-personnes/normes-et-standards-donnees-theoriques-et-temps-reel/tad-zonal) only says "_en cours de construction_". In practice, the PAN already hosts GTFS-Flex TAD feeds, such as [Aléop](https://transport.data.gouv.fr/datasets/transports-a-la-demande-en-pays-de-la-loire-gtfs-flex-aleop) and [TAO Orléans](https://transport.data.gouv.fr/datasets/description-de-loffre-tad-tao-gtfs-flex-orleans-metropole).
- **Planners that reuse PAN data** must not mislead the end user and must rank options neutrally ([user obligations](https://doc.transport.data.gouv.fr/le-point-d-acces-national/cadre-juridique/obligations-des-utilisateurs-de-donnees)). This matters if we show an unconfirmed Montenbus leg.

To feed Montenbus to MOTIS we need a GTFS-Flex dataset ([spec](https://gtfs.org/documentation/schedule/reference/)) containing:

- the pickup points as `stops.txt`, grouped in `location_groups.txt` and `location_group_stops.txt`;
- one trip with **two `stop_times` rows on the same group** (the spec's pattern for travel within one group or zone);
- `start/end_pickup_drop_off_window` of 06:45–19:30 with `pickup_type`/`drop_off_type = 2`;
- Monday–Saturday service with public holidays removed through `calendar_dates.txt`;
- `booking_rules.txt` with `booking_type=1`, `prior_notice_duration_min=15`, `prior_notice_duration_max=43200` (30 days), the phone number and `booking_url`;
- a separate `locations.geojson` polygon service for door-to-door PMR trips.

_Inference:_ GTFS-Flex cannot express membership, the ±15 min exclusion, the school-trip restriction or the 30-trips-per-month cap. Those stay as app-side text or filters.

[OpenTripPlanner](https://docs.opentripplanner.org/en/latest/sandbox/Flex/) also supports approved GTFS-Flex as a sandbox feature (`FlexRouting`), with access/egress and direct legs and experimental `safe_duration_*` support. It does not change the recommendation: MOTIS already covers the access/egress and direct cases Montenbus needs.

**Web app inspection (read-only, unauthenticated, 19 Nov 2026).** [montenbus.app.ridewithvia.com](https://montenbus.app.ridewithvia.com/) serves a 3,028-byte Flutter shell from S3/CloudFront. Its `version.json` is `{"app_name":"rider","version":"6.24.2"}`, `manifest.json` is empty, and `/.well-known/assetlinks.json` and `apple-app-site-association` return the same shell (no app-link files). Every path, including `/proposal?...`, returns HTTP 200 with that shell.

The public `main.dart.js` (9.9 MB) contains deep-link handlers for `/eligibility`, `/eligibility/letter` and **`/proposal`**. The `/proposal` handler reads these query parameters:

- `origin_lat`, `origin_lng`, `origin` (a label);
- `destination_lat`, `destination_lng`, `destination` (a label);
- `prebooking_request_type`, matched against `departure` or `arrival`;
- `prebooking_requested_time`, parsed as an integer whose unit was not determined.

A destination is required. Feature flags in the same bundle include `hasDeepLinkSupportPortal` (`eng-45782:rmv-deeplink-support`).

I did not run the app in a browser. So I could not verify whether the web build routes the browser URL into this handler, whether it is enabled for the Montenbus tenant, or whether it survives the login step. It is undocumented and could change without notice. Via's API terms forbid reverse engineering, so we should only build on it if Via confirms it as supported. Until then, link to the home page.

## Recommendation

1. **Ship A now.** It is cheap and fixes the main user-facing gap: the card does not say when or how booking is possible.
2. **Prototype D(b) behind a flag, not deployed publicly** until reuse is cleared. Use one location group with all stops, the rules in §4 and the ±15 min post-filter, and label legs "Montenbus — à confirmer sur réservation". If the results are poor, fall back to C.
3. **Send the request below.** Replace the self-authored feed with the official export as soon as it is published, and adopt B only once Via confirms it.
